# Catalpa 审阅线程设计

## 1. 选定的方案：版本差异重新定位，不把 OT 作为主模型

本实现选择 **版本差异 + 节点/文本证据重新定位（version-diff re-anchoring）**，而不是要求所有编辑经过操作变换（OT）。

原因：

1. 审阅锚点是一个带语义的区间，不只是数字位置。Markdown 重排、粗体语法变化、列表重写会把一个可见选区拆到多个节点，单纯 OT 位置变换会把批注锚到边界或标记字符。
2. 文稿存在离线编辑。OT 要求编辑在同一个操作序列中并发变换；离线端可以基于任意旧版本提交，服务端更适合保存版本、基线和三方合并结果。
3. 相同句子可能被复制到多处。只搜索相同文本或只按位置迁移都无法保证唯一对应，必须保留来源、置信度和人工裁决。

OT 仍可用于实时协作编辑器的光标和普通文本合并；审阅锚点在版本提交后，用以下证据重新定位：

- 旧源文档到新源文档的字符级 LCS 差异；
- 旧选区在差异中的保留比例；
- 选区原文精确匹配与标准化匹配；
- 前后 48 字上下文及上下文哈希；
- 块节点内容签名；
- 拆分后多个节点的 node range；
- 模糊匹配作为低置信候选，绝不静默自动接受。

## 2. 锚点数据

创建批注时，服务端保存：

```json
{
  "anchorFormat": 2,
  "documentVersion": 3,
  "sourceRange": { "start": 120, "end": 142 },
  "nodeRanges": [
    { "nodeId": "p-ab12...-0", "nodeType": "paragraph", "start": 0, "end": 22 }
  ],
  "quote": {
    "exact": "原始可见文本",
    "normalized": "原始可见文本",
    "hash": "..."
  },
  "context": {
    "before": "...",
    "after": "...",
    "beforeHash": "...",
    "afterHash": "..."
  },
  "baseline": {
    "documentVersion": 2,
    "contentHash": "..."
  }
}
```

`sourceRange` 是可审计的源文稿区间；`nodeRanges` 表示选区落在一个或多个渲染节点中的偏移；`quote` 和 `context` 用于差异证据不足时复核；`baseline` 固定创建或确认时的文稿版本和内容哈希。

## 3. 定位候选和置信度

每次文稿提交后，服务端对每个线程重新定位，结果有三种：

- `anchored`：唯一高置信候选，自动迁移，并写 `anchor.migrated` 事件；
- `candidate`：存在多个候选、证据冲突或置信度不足，事件记录候选，线程等待人工确认；
- `detached`：没有可信候选，线程悬挂，保留原锚点、原文和全部历史。

候选示例字段：

```json
{
  "source": "quote-exact",
  "confidence": 0.92,
  "sourceRange": { "start": 300, "end": 322 },
  "nodeRanges": [],
  "reasons": ["引用文本完全匹配", "前文上下文一致"]
}
```

自动接受阈值：

- 单一候选且置信度 `>= 0.90`；
- 或最高候选 `>= 0.90` 且比第二候选高至少 `0.08`；
- 其他全部进入人工确认。

相同引文复制到多处时，即使两处都是精确文本，也不会仅凭“找到同一句”迁移。上下文、版本差异和块签名共同决定是否能唯一定位。

## 4. 离线编辑合并

离线端记录：

- 编辑基线版本 `baselineVersion`；
- 本地文稿；
- 离线事件（回复、解决、重开）；
- 每个事件的向量时钟。

联网时：

1. 用 `diff3(base, local, remote)` 做行级三方合并；
2. 双方修改同一区域且结果不同，生成 `<<<<<<< local / ======= / >>>>>>> remote` 冲突标记，不隐藏冲突；
3. 非冲突文本形成新版本；
4. 离线事件按自身向量时钟追加，不覆盖远端事件；
5. 所有锚点基于合并后的新版本重新定位；
6. 若锚点位于冲突区域或找不到可信证据，进入候选或悬挂状态。

## 5. 解决状态与内容绑定

解决事件保存当时被评阅内容的 `contentHash`：

```text
thread.resolved(payload.contentHash)
```

随后：

- 内容移动但原引用未变：结论随锚点迁移，仍视为针对同一内容的结论；
- 内容被删除：线程悬挂，旧结论保留；
- 原句重写且哈希不同：状态为 `needs_review` 或悬挂，可发起新一代审阅；
- “重新请求审阅”递增 `reviewGeneration`，追加 `review.requested`，不删除旧的 resolve 事件和旧结论。

## 6. 并发解决与重开

回复、解决、重开均为不可变事件。向量时钟判断：

- 因果事件：按发生顺序归约；
- 并发解决/重开：两者都保留，并追加 `thread.concurrent-conflict`；
- UI 显示冲突，由人工选择最终状态，系统不按最后写入覆盖。

## 7. 旧前端保护

旧前端只理解 `sourceRange`，不理解候选、来源、置信度和锚点代次。服务端/响应层使用 `anchor_epoch` 与 `legacyPayloadGuard`：

- 未发生迁移时旧客户端可显示；
- 一旦出现 `anchor.migrated`、`anchor.candidate` 或 `anchor.attached`，旧客户端必须隐藏批注；
- 不允许旧客户端拿缓存的旧 `sourceRange` 在新文稿上重新计算位置。

## 8. SQL 事件模型

见 `server/schema.sql`：

- `document_versions`：不可变版本和合并报告；
- `review_threads`：当前投影；
- `review_events`：回复、解决、重开、迁移、冲突等不可变事件；
- `anchor_candidates`：候选来源、置信度、原因和人工决策；
- `offline_operations`：离线编辑与事件队列。

## 9. 已覆盖的测试场景

`tests/review.test.js` 覆盖：

1. 锚点保存源范围、节点范围、上下文、基线；
2. 整段移动；
3. 同一引文多处出现；
4. 选区删除；
5. 编辑后选区拆到多个节点；
6. 原句重写后保留旧结论并重新请求审阅；
7. 离线三方编辑合并及冲突标记；
8. 离线回复、并发解决和重开，事件历史完整；
9. 旧前端隐藏已迁移锚点，禁止使用过期位置。
